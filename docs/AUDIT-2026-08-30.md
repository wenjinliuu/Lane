# Lane 横向审计报告

审计日期：2026-08-30
审计基线：`b278ec9`（`dist/metadata.json` v2fly `06111d32`，profile 共 40,437 条）
审计立场：**Lane 的定位是"懒人配置"——默认可用、少概念、少维护。** 下面所有建议都按这个前提取舍；
凡是要求用户理解 MITM、脚本、复写、广告规则的东西，本报告一律不建议加。

对照项目（只作事实核对与覆盖度对照，**未复制任何规则内容**）：
Repcz/Tool、QuixoticHeart/rule-set、Moli-X/Resources、Loon 官方 example.conf、
Loyalsoldier/v2ray-rules-dat、v2fly/domain-list-community。

---

## 0. 总评

Lane 在**工程质量**上明显强于绝大多数同类项目：声明式配置、六端统一生成、
full/profile 拆分、CN-IP 七日窗 + 熔断 + 独立交叉验证、golden route case、许可与 NOTICE 完整。
这些同类项目基本没有。

差距不在工程，而在**成品配置的运行时默认值**和**规则语义**这两块：

| 维度 | Lane | 同类活跃项目 |
| --- | --- | --- |
| 生成器/可复现性 | 强（唯一有熔断+交叉验证的） | 多数手写或简单脚本 |
| 规则来源可追溯 | 强（SHA256 + commit 记录） | 弱 |
| DNS 配置 | 六端全部裸奔用 system | 全部显式配置 + 加密 DNS |
| UDP/QUIC 回落 | 六端全部未设置 | 全部设置 |
| 大陆托管的境外品牌域名 | 走代理（见 §1.1） | 明确判直连 |
| 规则体积 | 40,437 条 | 一般 1–2 万 |
| dist 发布方式 | 每天提交进 `main` | 独立 release 分支 + jsDelivr |

按优先级：**§1 和 §2 是会让懒人用户直接踩坑的；§3、§4 是优化。**

## 1. P0：路由正确性

### 1.1 `proxy` 规则集抢在 `china` 之前，把 347 条大陆托管域名送进了代理

`config/rulesets.yaml` 把 v2fly `geolocation-!cn` 作为 `proxy` 集放在 `china` 之前，
注释里写的理由是"抢在 China / CN IP / GEOIP 之前接住已知境外域名"。

问题在于 **`geolocation-!cn` 的语义是"这家公司/服务不是中国的"，不是"这个服务器不在中国"**。
外企的 `.cn` / `.com.cn` 站点两边都在，Lane 的顺序让它们一律判代理。

实测（`dist/stash/rules-profile/proxy.list` 对 `china.list` 求覆盖）：

- full 产物中重叠 **575 条**
- profile 残余里仍然活着 **347 条**（其余被更前面的规则集提前认领了）

其中明确应当直连、走代理会变慢或直接坏掉的：

| 类别 | 条数 | 例子 | 后果 |
| --- | --- | --- | --- |
| 大陆 NTP | 17 | `ntp.aliyun.com`、`ntp.tencent.com`、`ntp.ntsc.ac.cn`、`cn.pool.ntp.org` | 对时走代理，延迟高、部分节点封 UDP 123 |
| NAS / 内网发现 | 4 | `quickconnect.cn`、`myqnapcloud.cn`、`synology.cn`、`qnap.com.cn` | 群晖/威联通远程发现失败 |
| AWS 中国 | 2 | `amazonaws.cn`、`amazonaws.com.cn` | 宁夏/北京区（光环新网、西云）走代理，反而不可达 |
| 大陆金融 | 12 | `hsbc.com.cn`、`ru.ccb.com`、`visa.com.cn`、`mastercard.cn`、`paypal.com.cn` | 风控 / 地域校验触发 |
| 外企大陆站 | 200+ | `nike.cn`、`ikea.cn`、`mcd.cn`、`starbucks.com.cn`、`adidas.cn` | 纯粹变慢 |

交叉验证：`ntp.aliyun.com` 在 Loyalsoldier `direct-list.txt` 里、**不在** `proxy-list.txt` 里；
`8686c.com`（Steam 中国 CDN）同样只在 direct-list。说明 Loyalsoldier 的构建流程会**主动消解**
这两个列表的冲突，Lane 目前是"proxy 无条件赢"。

同时也要说清楚：Loyalsoldier 并非把 575 条全判直连。精确匹配统计中，
**52 条判直连、51 条仍判代理**（`google.cn`、`bloomberg.cn`、`airbnb.cn` 等），其余被父级后缀覆盖。
所以正确的做法不是"删掉 `proxy` 集"，而是**给冲突一个显式策略**。

**建议（按代价从低到高）**

1. **最小改动**：在 `rules/custom/direct.list` 里加一个短白名单，把上表前四类（约 35 条）
   钉成直连，位置在 `custom-direct`（已经排在 `proxy` 之前）。
   代价：一个手工维护的小文件；收益：覆盖 90% 的实际痛点。
2. **结构改动（推荐）**：在编译期做冲突消解——`proxy` 集减去 `china` 集已覆盖的条目，
   把差集单独产出为 `proxy-guard`，再对少量"确实要代理的 `.cn`"（`google.cn` 等）
   做显式 keep 名单。这样 `proxy` 集从 18,785 条降到几百条（见 §3.3）。
3. 在 `tests/route_cases.yaml` 里加 golden case：`ntp.aliyun.com → DIRECT`、
   `quickconnect.cn → DIRECT`、`google.cn → Google`，防止回归。

### 1.2 `apple.com.cn` / `icloud.com.cn` / `azure.cn` / `office365.cn` 默认走代理

这条和 1.1 是同一个病因的另一半，但被 README 的 AppleCN 说明掩盖了。

实测落点（`dist/stash/rules-profile/`）：

```
apple.com.cn        -> apple.list       -> Apple 组     -> 默认 Manual（代理）
icloud.com.cn       -> apple.list       -> Apple 组     -> 默认 Manual（代理）
azure.cn            -> microsoft.list   -> Microsoft 组 -> 默认 Manual（代理）
office365.cn        -> microsoft.list   -> Microsoft 组 -> 默认 Manual（代理）
microsoftonline.cn  -> microsoft.list   -> Microsoft 组 -> 默认 Manual（代理）
```

`apple-cn` 规则集（felixonmars，169 条）**不包含** `apple.com.cn` / `icloud.com.cn`——
它是 DNS 加速名单，只覆盖 `mzstatic.com`、`appldnld.apple.com` 这类 CDN 主机名，
不覆盖苹果中国的品牌域名。所以 README 里"AppleCN 优先直连"的保护范围比读者预期的窄。

**这里有个现成的、许可干净的解法：v2fly 已经用 `@cn` 属性标好了。**

```
$ curl .../data/apple     | grep -c '@cn'   -> 207
$ curl .../data/microsoft | grep -c '@cn'   ->  86
$ curl .../data/google    | grep -c '@cn'   -> 114
```

Lane 的解析器（`src/proxyrules/v2fly.py:_attributes`）**已经把 `@cn` 读进 `Rule.attributes` 了**，
只是 `config/rulesets.yaml` 没有暴露属性过滤。建议加一个字段：

```yaml
- id: apple-cn
  title: AppleCN
  policy: DIRECT
  v2fly: [apple]
  v2fly_require: [cn]        # 新增：只取带 @cn 的条目
  text_source: apple_cn      # 与 felixonmars 合并

- id: microsoft-cn           # 新增，放在 microsoft 之前
  title: MicrosoftCN
  policy: DIRECT
  v2fly: [microsoft]
  v2fly_require: [cn]
```

收益：
- 一次改动同时修好 Apple / Microsoft / （如果将来需要）Google 三条线；
- 数据源仍是 v2fly（MIT），不引入新上游、不抄任何 GPL/AGPL 项目；
- 与 §1.1 的建议 2 共用同一套属性过滤机制。

注意 GoogleCN 保持现状——README 里那段论证（`dl.google.com`、`clientservices.googleapis.com`
直连失败）是对的，`@cn` 属性也救不了它，不要因为对称性就把它加回默认分流。

### 1.3 没有处理 HTTPDNS

同类项目普遍有一个 `httpdns` 规则集（QuixoticHeart 有 `httpdns.list`）。
阿里/腾讯 HTTPDNS（`203.107.1.x`、`119.29.29.98/99` 等）让 App 绕过系统 DNS 直接拿 IP，
结果是**这些 App 的流量完全绕开 Lane 的域名规则**，只剩 `cn-ip` / `GEOIP` 兜底。

对懒人配置来说这不是理论问题：抖音、淘宝、B 站、部分银行 App 都用。

**建议**：加一个约 20 条的 `httpdns` 集，`policy: DIRECT`，放在 `lan` 之后。
不要用 REJECT（Lane 明确不做 REJECT，而且 REJECT 会让部分 App 反复重试）。
判直连即可——目的是保证它们不被 `cn-ip` 之外的规则误判。数据可从 v2fly + 自维护小列表得到。

## 2. P0：懒人可用性（六端 `[General]` 默认值）

这是 Lane 与所有对照项目差距最大的地方。Lane 六份主配置的全局段几乎是空的。

### 2.1 完全没有 UDP / QUIC 回落策略 —— 六端全缺

| 客户端 | 对照项目的写法 | Lane |
| --- | --- | --- |
| Surge | `udp-policy-not-supported-behaviour = REJECT` | 未设置 |
| Shadowrocket | `udp-policy-not-supported-behaviour = REJECT`、`block-quic = all-proxy` | 未设置 |
| Loon | `udp-fallback-mode = REJECT`（Repcz）/ `DIRECT`（Moli） | 未设置 |
| Quantumult X | `fallback_udp_policy = reject`、`udp_drop_list = QUIC` | 未设置 |
| Stash / Egern | 依赖客户端默认 | 未设置 |

**为什么这是懒人问题**：机场节点普遍不支持 UDP 中转。不设回落时，
YouTube / Google 的 QUIC(UDP 443) 会尝试走代理然后静默超时，
表现是"网页转圈、视频卡住，但换个 App 又正常"——普通用户完全无法自己诊断。
设成 `REJECT` 后浏览器会立刻回退 TCP/TLS，体验直接正常。

**建议**：在 `config/project.yaml` 加一组 `runtime:` 默认值，六端渲染器各自映射。
这是本报告里**投入产出比最高的一项**。

### 2.2 `Manual` 是纯手选组，选中的节点挂了就全挂

当前 `Manual = select`（Surge/Loon/SR/QX/Stash/Egern 一致），
`Final` 默认跟随 `Manual`，所有服务组默认也跟随 `Manual`。
也就是说**整份配置的可用性系于用户手选的那一个节点**。节点掉线时没有任何自动切换。

对照项目一律有一个自动组兜底（Repcz 的 `HongKong/United States/...` 都是 `url-test`/`smart`，
`Global` 指向它们；Moli 的 `全球节点 = url-test`）。

**建议（保持"只有一个手选入口"的设计，不增加概念）**：
新增一个 `Auto = url-test`（全节点，正则 `.+`，复用现有 benchmark 参数），
把它作为 `Manual` 选项列表的**第一项**，并让 `Final` 的默认选择指向 `Auto` 而不是 `Manual`。
用户什么都不改就有自动优选；想手选照旧进 `Manual`。策略组只多一个，不违背懒人定位。

### 2.3 DNS 六端全部裸奔

| 客户端 | Lane 当前 | 对照项目 |
| --- | --- | --- |
| Surge | `dns-server = system` | `dns-server = 223.5.5.5, 119.29.29.29` + `encrypted-dns-server = https://doh.pub/dns-query, https://dns.alidns.com/dns-query` |
| Loon | 未设置 | `dns-server = 223.5.5.5,119.29.29.29`（Repcz）/ 加 `doh-server`（Moli） |
| QX | `[dns]` 只有 `no-ipv6` | `no-ipv6` + `no-system` + `server=223.5.5.5` + `server=119.29.29.29` |
| Stash | `dns:` 只有 `fake-ip-filter` | `nameserver: [223.5.5.5, 119.29.29.29]` |
| Egern | `forward: * -> bootstrap(system)` | 分组上游 + `proxy_nameservers` |
| Shadowrocket | 未设置 | `dns-server` + `fallback-dns-server = system` |

`system` DNS 在国内运营商网络下有两个后果：
（a）被劫持/污染的应答直接影响 `cn-ip` 和 `GEOIP,CN` 这两层兜底的判断；
（b）在部分校园网/公司网下解析结果和路由完全对不上。

**建议**：至少写 `223.5.5.5, 119.29.29.29`（这也是所有对照项目的共识值），
Surge/Loon 额外给一行加密 DNS。不需要做 Egern 那样的分组转发——那超出懒人范围。

另外 `hijack-dns` 目前只有 `8.8.8.8:53, 8.8.4.4:53`，
对照项目用 `*:53`（Surge/SR/Egern 都是）。写死两个地址只能劫持指定 Google DNS 的应用，
路由器/智能设备指向 `114.114.114.114` 的一律漏掉。**建议改成 `*:53`。**

### 2.4 其余缺失的全局项（逐端对照）

**Surge**

| 键 | 建议值 | 理由 |
| --- | --- | --- |
| `exclude-simple-hostnames` | `true` | 单标签主机名（`nas`、`router`）不进代理栈 |
| `skip-proxy` | 私有网段 + 常见银行/一键登录域名 | 部分银行 App 走代理栈直接失败 |
| `internet-test-url` | `http://wifi.vivo.com.cn/generate_204` | 现在只有 `proxy-test-url`，网络状态判断用的是默认值 |
| `ipv6-vif` | `auto` | 与 `ipv6 = false` 搭配，见 §3.2 |
| `geoip-maxmind-url` | 自定义 mmdb | Lane 把 `GEOIP,CN` 当第二层兜底，但没管这层的数据质量 |
| `show-error-page-for-reject` | `true` | 无 REJECT 规则时无害，将来有用 |

`always-real-ip` 建议补 `<simple-hostname>`、`lancache.steamcontent.com`、
`*.prod.cloud.netflix.com`、`appboot.netflix.com`。

**Loon**：`ipv6 = false` 建议改用 Loon 现行的 `ip-mode = ipv4-only`
（Repcz 与 Moli 都用 `ip-mode`；`ipv6` 疑似旧键）。另缺
`sni-sniffing = true`、`disconnect-on-policy-change = true`、`interface-mode = auto`、
`internet-test-url`、`skip-proxy`。其中 `disconnect-on-policy-change` 直接影响
"我切了策略组但没生效"这类最常见的用户困惑。

**Shadowrocket**：缺 `bypass-system = true`、`dns-server`/`fallback-dns-server`、
`hijack-dns = *:53`、`private-ip-answer = true`、`icmp-auto-reply = true`。

**QX**：缺 `network_check_url`。`dns_exclusion_list` 建议补运营商一键登录域名
（`*.cmpassport.com`、`id6.me`、`open.e.189.cn`、`auth.wosms.cn`、`*.10099.com.cn`）——
这些走 fake-ip 会让"本机号码一键登录"失败，是国内配置的经典坑。
同样的清单也应进 Stash 的 `fake-ip-filter` 和 Surge/Loon/SR 的 `always-real-ip`。
**这一条对懒人体验的价值仅次于 §2.1。**

**已确认没有问题的两点**（本次核对过，可以放心）：
- Loon `[Remote Filter]` 不写订阅来源（`X = NameRegex, FilterKey = "..."`）是社区通行写法，
  Moli 的配置就是这么写的，不需要改成官方 example 里的 `NameRegex,Subs,FilterKey=` 形式。
- Loon 把 `GEOIP,CN,DIRECT` + `FINAL` 放 `[Rule]`、规则集放 `[Remote Rule]`，
  与 Loon 官方 example.conf、Repcz、Moli 的写法完全一致，**没有理由认为 Lane 写错了**。

  但有一个遗留疑点值得真机确认：社区资料普遍描述 Loon 的匹配优先级是
  "本地规则 > 插件规则 > 订阅规则"。若字面成立，`[Rule]` 里的 `GEOIP,CN,DIRECT`
  会跑在全部 22 个远程规则集之前，等于把大陆判定提前到第一步。
  官方 example.conf 自己也是这么写的，说明 `FINAL` 至少是被特殊处理成最后一条的，
  但 `GEOIP` 是否同样被排到远程规则之后，无法从公开文档确认。

  **验证方法**：导入 Loon 后访问一个"域名在 `proxy`/服务集里、但解析结果落在 CN 段"的目标
  （例如某个用了国内 CDN 的境外站），看请求日志里命中的是远程规则 tag 还是 `GEOIP`。
  如果是 `GEOIP`，需要把 Loon 的 `GEOIP,CN,DIRECT` 从 `[Rule]` 移除，
  改为在 `cn-ip` 之后再挂一个远程 GeoIP 兜底，或直接依赖 `cn-ip` 单层。

## 3. P1：规则体积与性能

### 3.1 Stash 的 22 个 rule-provider 全是 `behavior: classical`

QuixoticHeart 的项目背景里专门写了这点：mihomo/Stash 对 `domain` 和 `ipcidr` 类型的规则集
做了针对性优化，**性能受限设备上应避免 classical**。Lane 目前 22 个全是 classical，
其中 `proxy` 18,785 条、`cn-ip` 9,374 条、`china` 5,995 条。

Lane 的规则集**已经是按类型拆开的**（`brokerage`/`brokerage-ip`、`telegram`/`telegram-ip`、
`cn-ip` 独立），所以这个改造几乎是免费的：

- 19 个纯域名集 → `behavior: domain`
- `cn-ip` / `telegram-ip` / `brokerage-ip` → `behavior: ipcidr`
- `lan` 混合了 118 域名 + 18 网段 → 拆成 `lan` + `lan-ip`

唯一障碍是 `behavior: domain` 不支持 `DOMAIN-REGEX`。实测只有 8 个集有正则，共 160 条，
其中 146 条集中在 `proxy`（内容基本是成人站域名轮换）：

```
proxy 146 / streaming 5 / gaming 3 / google 2 / ai 1 / china 1 / developer 1 / lan 1
```

**建议**：把这 160 条正则单独产出为一个 classical 的 `regex` 集，其余全部改成 domain/ipcidr。
Egern 同理（它原生保留 `domain_regex_set`，本来就分类型，无需改）。

### 3.2 `ipv6: false` 与 3,436 条 IPv6 规则自相矛盾

六端主配置全部关闭 IPv6，但 profile 产物里有 **3,436 条 `IP-CIDR6`**（占总量 8.5%），
其中 `cn-ip` 贡献 3,427 条。IPv6 关闭时这些规则永远匹配不到，纯粹是下载量和内存开销。

**二选一，不要维持现状：**

- **方案 A（省事）**：profile 产物过滤掉 IPv6 规则，full 产物保留完整双栈。
  立省 8.5% 体积，路由结果零变化。`cn_window.py` 的双栈校验逻辑全部保留，不影响 §审计价值。
- **方案 B（跟上趋势）**：打开 IPv6（Loon `ip-mode = dual` / Surge `ipv6 = true, ipv6-vif = auto`）。
  但这会引入一批新的真机验证工作（节点是否支持 v6、CN v6 判定是否准），
  **不符合懒人定位，不推荐现在做**。

倾向 A。同时把 README 里"CN IP 双栈"的表述改为"full 产物双栈、profile 产物随 IPv6 开关"。

### 3.3 `proxy` 集用 18,785 条规则去实现一个"顺序守卫"

README 自己写清楚了：`proxy` 的策略就是 `Final`，和 `MATCH` 同一个出口，
存在的唯一意义是抢在 `china` / `cn-ip` / `GEOIP` 之前。也就是说 **46% 的规则体积
不改变任何一条流量的出口，只改变判定顺序。**

它实际起作用的只有两部分：
1. 与 `china` 冲突的 575 条（其中 347 条在 profile 里还活着）——而这正是 §1.1 说的**误判来源**；
2. 域名不在 `china` 里、但 IP 落在 CN 段、会被 `cn-ip`/`GEOIP` 误判的那些——**数量未知，无法离线测算**。

**建议**：
- 短期：接受现状，但按 §1.1 修掉冲突方向；
- 中期：把 `proxy` 换成两个集——`proxy-guard`（= `geolocation-!cn` ∩ `china`，经显式裁决，几百条）
  + 可选的 `proxy-full`（放 `rules-full/`，供想要完整语义的用户手工引用）。
  在做之前，先用真机抓一批"域名不在 china、IP 在 CN 段"的样本量化第 2 部分的价值——
  **不要在没有数据的情况下直接删。**

体积参考：`proxy` + `cn-ip` + `china` = 34,154 条，占 profile 的 84%。
其余 19 个集加起来才 6,283 条。

## 4. P1：工程与发布

### 4.1 `dist/` 每天提交进 `main`

`.github/workflows/update.yml` 每天把变化的 `dist/` 直接 commit 到 `main`。
按当前体积，一年后 `main` 的历史会积累相当可观的 diff，`git clone` 会明显变慢，
而且源码提交会被自动提交淹没。

对照项目**全部**把产物放独立分支：
Loyalsoldier → `release`、MetaCubeX → `meta`、Repcz → `X`、QuixoticHeart → `ruleset`。

**建议**：产物推到 orphan 分支（如 `dist`，force-push 覆盖），`main` 只留源码。
`config/project.yaml` 的 `raw_base` 改成指向该分支即可，主配置里的 URL 结构不变。
代价：用户需要升级一次主配置——但 §1、§2 的修复本来就要求升级一次，**建议合并成一次发布**。

### 4.2 建议同时给 jsDelivr 地址

`raw.githubusercontent.com` 在国内直连成功率不稳定。Lane 的规则更新 URL
会命中 `developer` 规则集 → Developer 组 → 默认代理，所以**节点可用时没问题；
节点不可用时规则也更新不了**。QuixoticHeart 直接主推 jsDelivr。

**建议**：README 的表格里给出 jsDelivr 镜像作为备选一行，不改默认值。零维护成本。

### 4.3 Surge 图标的结论可能是反的

README 写"Surge 的官方 `icon-url` 当前标注为 Mac 功能，本配置以 iOS 兼容为先，不设置它"。
但 Repcz 的 Surge 配置（面向 iOS+Mac）大量使用 `icon-url=B1::Logos::...`，
而 Surge 社区里能查到的相关讨论标题是《mac 端不支持 icon-url 吗？》——
指向的是**相反**的情况。

**建议**：真机核对一次。如果 iOS 支持，就把 Surge 与其余五端拉齐加上图标——
这是纯收益的一致性改进。（本报告未能拿到官方手册原文，`manual.nssurge.com` 在本次审计环境被出口策略拦截。）

### 4.4 Shadowrocket 的 `update-url` 与"本地保存"的文档口径冲突

README 反复强调"主配置本地保存，不跟随远程整份更新"，
但 `dist/shadowrocket/Lane_shadowrocket.conf` 里写了
`update-url = https://raw.githubusercontent.com/.../Lane_shadowrocket.conf`。
Shadowrocket 会据此整份刷新配置，覆盖用户改动。

**建议**：要么删掉这一行，要么在 README 的 Shadowrocket 行明确说明它是有意保留的例外。
两种都行，但目前是文档和产物不一致。

## 5. 建议**不要**做的事（守住懒人定位）

对照项目里有一堆东西，Lane 应当继续拒绝：

- **广告拦截 / REJECT 规则**：已明确不做，正确。加了就要处理误杀、`dns-reject-mode`、
  白名单维护，全是长期负担。anti-AD / AdRules 保持"可选独立 ruleset"的定位即可，不进默认配置。
- **MITM / 复写 / 脚本 / 插件**：Repcz、Moli、QX 社区配置里占篇幅最大的部分。
  需要装证书、需要理解 hostname，与懒人定位直接冲突。
- **更多地区组**：现在 5 地区 × 2 = 10 个组已经在列表末尾了。加韩国/英国/德国会让策略页更长，
  而这些节点仍然可以从 `Manual` 里直接选。
- **`load-balance` / `fallback` 等更多组类型**：`select` + `url-test` 两种足够。
- **按 App 分流（PROCESS-NAME）**：iOS 上不可用，只对 Surge Mac 有意义。
- **Egern 那种分组 DNS 转发**：Repcz 的 Egern 配置里 DNS 段有 40 多行，功能强但概念多。
  Lane 按 §2.3 写两个国内 DNS 就够。

### 6.2 那么到底该怎么用这些项目

**三种用法，法律风险和工程代价完全不同：**

1. **引用远程 URL（`RULE-SET` 指向对方的 raw 地址）——不构成复制，任何许可都没问题。**
   Repcz 的 README 就是这么教的。代价是：Lane 失去对该规则集的可复现性
   （`metadata.json` 记不了对方的 commit 和 SHA256），并且把可用性绑在别人的仓库上。
   **与 Lane 的核心卖点冲突，不推荐作为默认配置的一部分。**

2. **作为差分审计参照——零风险，且 Lane 已经在这么做了。**
   `config/sources.yaml` 里 Loyalsoldier/geoip 标着"仅用于人工差分审计，不参与构建"，
   misakaio 标着 `role: validation-only`。**这个模式是对的，应该扩大使用**：
   比如拿 blackmatrix7 的 Netflix 列表和 Lane 的 `streaming` 做差分，
   把"我们缺了哪些域名"作为**问题清单**，再回 v2fly 提 PR 或写进 `rules/custom/`。
   差分结果是事实陈述，不是对方代码的衍生作品。

3. **直接复制内容——只有 MIT/WTFPL 那几个可以无痛做。**
   Repcz（MIT）是里面质量最高又最好用的，需要补某个具体服务的域名时可以直接拿，
   在 `NOTICE.md` 和对应 `licenses/` 里加一份 MIT 声明即可，和现有的
   gaoyifan-MIT.txt 一个做法。

**GPL 那几个：不是"不能用"，是"用了要换许可"。** 把 blackmatrix7 的规则文件复制进
`dist/` 并分发，那些衍生文件就要按 GPL-2.0 提供，实践上等于整个仓库转 GPL。
这是个可以做的决定，只是要**主动决定**，而不是不小心滑进去。

（值得一提：域名列表这种"事实汇编"是否受版权保护，本身在法律上有争议。
但社区惯例是按许可对待，Lane 既然已经建立了 `licenses/` + `NOTICE.md` 的规范，
就没有理由在这里破例。）

### 6.3 但比许可更重要的是：复制会破坏 Lane 的核心优势

即使全部换成 MIT 项目、法律上完全自由，**大规模复制规则内容对 Lane 仍然是错的**：

1. **可复现性没了。** Lane 现在每一条规则都能追到 v2fly 的 commit hash 或文本源的 SHA-256。
   手工复制进来的一份快照没有上游指针、没有更新路径、没法判断是否已经过期。
   Lane 就从"生成的"退化成"生成的 + 一堆手抄件"。
2. **多了一跳陈旧度。** 这些项目大多也是从上游整理来的（QuixoticHeart 自称"收集于互联网"）。
   复制它们往往是复制"快照的快照"。
3. **顺序假设会一起被带进来，而且会坏事。** 别人的规则集是按**他们的**规则顺序和策略组设计的。
   本报告 §1.1 那 347 条误判，病因正是"引入了一个列表却没引入它的排序前提"。
   直接抄 blackmatrix7 的 `Netflix.list` 放进 Lane 的第 10 位，很可能重演同一类问题。
4. **维护成本翻倍。** 22 个集来自一个生成器，和 22 个集来自 5 个上游、5 种更新节奏，
   完全是两个量级的负担——对一个"懒人项目"尤其致命。

**结论：把这些项目当成"问题发现器"，而不是"内容来源"。**
用它们的覆盖度找出 Lane 缺什么（这正是 §6 那张表的做法），
然后用 v2fly 属性、上游 PR 或 `rules/custom/` 里几十行自维护规则去补。
需要小范围直接复用时，优先 Repcz（MIT）。
