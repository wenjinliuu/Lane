## 1. 执行摘要

Lane 当前的主体结构是成立的。"单一规则意图 + 客户端专用渲染 + 结构校验"这条主线在代码里是真实存在的，不是文档里的说法：`config/rulesets.yaml` 的顺序被 `src/proxyrules/config.py` 用硬断言锁住，`src/proxyrules/validate.py` 逐端反解生成物并与清单比对，CN-IP 的七日窗、熔断与 last-known-good 缓存在 `src/proxyrules/upstream.py` 中是完整实现的。同类项目里，很少有把"发布前反解自己的产物再校验一遍"做到这个程度的。

**本轮结论是：不需要重大架构升级；但有 1 个确认的路由缺陷、4 个值得近期实施的工程改进。**

三个最重要的结论：

1. **`apple-cn` 抢占了 Apple Music / Apple TV+ 的 Streaming 规则**，与 `docs/DECISIONS-2026-08-30.md` D2 明确记录的"Apple TV+、Apple Music 等更具体业务规则继续优先匹配"相反。六端一致地把 `music.apple.com`、`itunes.apple.com` 及其子域判为 `DIRECT`，用户在 `Streaming` 组里的选择对这两项服务完全失效。这是本轮唯一的 P0。
2. **六端语义一致性目前只在 Stash 上被验证过**。`tests/test_route_cases.py` 的 20 条黄金用例只对 `dist/stash/Lane_stash.yaml` 求值。我用同样的首次命中逻辑重放六端产物，20 条现有用例六端完全一致（说明基线是好的），但另外构造的 10 条边界用例里有 9 条发散——其中 `lan` 的单标签主机名正则在 Loon / Shadowrocket / Surge / QX 上被省略，裸主机名（`nas`、`router`）会一路穿透到 `Final` 被代理出去。这是 174 条省略里唯一一条会造成泄漏的。
3. **上游保护是不对称的**。CN-IP 有七日窗、地址空间对称差熔断、staging 原子替换和 last-known-good；而 `telegram_cidr`、`apple_cn`、`cn_ipv4_reference` 三个单文件源只有"能解析且非空"这一层。同时 CI 里 `.cache/` 被 gitignore 且没有 `actions/cache`，所以 `upstream.py` 里那条"网络失败时回退缓存"的路径在 GitHub Actions 上**从不生效**——任何一个上游抖动都会让当天全部更新停摆。

没有发现必须在今天之内热修的安全问题。P0 的性质是"功能与设计意图不符"，不是泄漏或凭据风险。

**关于 Quantumult X 的 `no-resolve`（已核实，可作为 Keep 依据）**
我拉取了官方 `crossutility/Quantumult-X` 仓库的 `sample.conf`（`v1.5.5 build 914`，访问日 2026-08-30）。`[filter_local]` 段列出的全部规则类型是：`user-agent` / `host` / `host-keyword` / `host-wildcard` / `host-suffix` / `ip6-cidr` / `ip-cidr` / `geoip` / `ip-asn` / `final`。**没有 `host-regex`，也没有任何 `no-resolve` 修饰符**。Lane 现在既不发 `no-resolve` 也不发正则，与官方示例完全吻合。同一份示例还写明"DNS 服务器默认取自系统，除非设置 `no-system`"，这正面支持了 PR #4 删除 `server = system` 的决定。

同时注意到官方示例中一条值得记录的说明：`host-keyword, ., proxy` 可以用来"跳过所有未匹配主机的 DNS 查询"。这反过来证明：在 QX 里，未被域名规则命中的请求**会**为了评估 `ip-cidr` 规则而发起 DNS 解析。Lane 的 `cn-ip` 有意不带 `no-resolve` 正是要利用这一点，语义方向一致。

**关于 Surge 的 DOMAIN-REGEX（证据不足，需要维护者在客户端内确认）**
本次审计环境的出站策略屏蔽了 `manual.nssurge.com` 与 `kb.nssurge.com` 的直接访问，我只能通过搜索索引读取页面片段，结论有冲突：
- 一次检索返回的片段声称 Surge 支持 `DOMAIN-WILDCARD` 与 `DOMAIN-REGEX`，但同一批结果里混入了 `stash.wiki/en/rules/rule-types`，很可能是把 Stash 的规则类型串到了 Surge 条目上；
- 把检索限定在 `manual.nssurge.com` 后，`Domain-based Rule` 页面返回的类型只有 `DOMAIN` / `DOMAIN-SUFFIX` / `DOMAIN-KEYWORD` / `DOMAIN-SET`；
- 独立佐证：blackmatrix7 的 `rule/Surge/Netflix/Netflix.list` 文件头逐类型统计为 `DOMAIN / DOMAIN-KEYWORD / DOMAIN-SUFFIX / IP-CIDR / IP-CIDR6 / PROCESS-NAME / USER-AGENT`，**不含 DOMAIN-REGEX**；其 QX 版本则出现了 `HOST-WILDCARD`。

**因此本报告维持 Lane 现状（Surge 省略正则）为默认结论，置信度中等。** 如果维护者能在 Surge 内实测 `DOMAIN-REGEX` 于 `RULE-SET` 文件中可加载，L-03 中 Surge 的部分可以直接改成"不转换、原样保留"，工作量归零。这一条不要靠推断决定。

同一批检索还提示 Surge 5 存在 `HOSTNAME-TYPE` 规则类型，取值包含 `IPv4 / IPv6 / DOMAIN / SIMPLE`。若属实，`HOSTNAME-TYPE,SIMPLE,DIRECT` 是 L-02 在 Surge 上的官方等价写法，且它**不是**已被明确否决的 `exclude-simple-hostnames`（后者是 `[General]` 开关，前者是规则）。同样标记为需要实测，不在本轮下结论。

### 4.3 174 条 DOMAIN-REGEX 的逐类分析

分布：`proxy` 158 条，其余 16 条分散在 `lan`(1) `ai`(1) `streaming`(5) `gaming`(3) `developer`(1) `google`(2) `china`(3)。

**(a) `proxy` 的 158 条 —— 结论：继续省略，风险低但非零。**
`proxy` 的策略是 `Final`，与最终 `MATCH,Final` 相同，所以省略这些正则**不会改变最终出口策略**。但按 D1 的设计，`proxy` 的价值在于"位置"：它在 `telegram-ip` / `cn-ip` / `GEOIP,CN` 之前把已知境外域名接住。省略之后，只被这些正则匹配的主机名在四端会继续下落，一旦解析到 CN 段就会被 `cn-ip` 或 `GEOIP,CN` 判为 `DIRECT`。这类主机名多为 CDN 边缘节点，理论上存在被大陆 CDN 解析命中的可能。其中 12 条本就被更早或同集的 `DOMAIN-SUFFIX` 覆盖（5 条被 `china` 抢先，其余被同集后缀覆盖），属于死规则。**建议：不做全局转换；若日后要收敛，只对确证会解析到 CN 段的少数条目单独加白名单。**

**(b) 其余 16 条 —— 逐条转换白名单（本轮只给方案，不改代码）**

## 5. 上游与供应链审计

### 5.1 各上游的实际使用方式与风险

| 源 | 用法 | 抓取方式 | 现有保护 | 失效风险 |
|---|---|---|---|---|
| `v2fly` | 域名主源，22 个规则集中 19 个用到 | `git clone --depth 1 --branch master`，随后 `git fetch --depth 1 + merge --ff-only` | revision 记录进 `metadata.json` | **强推历史会让 `--ff-only` 失败并直接抛 `UpstreamError`，且没有回退到已缓存 clone 的分支**（对比：文本源有回退）。仓库迁移/改名同样直接中断构建 |
| `gaoyifan/china-operator-ip` | CN-IP 唯一发布主源 | clone `--depth 32 @ ip-lists`，取最近 7 个不同 UTC 日期的快照 | 七日窗 5/7 + 双栈校验 + 1% 地址空间对称差熔断 + staging 原子替换 + last-known-good；克隆失败时**有**缓存回退 | 保护充分。唯一残余风险是仓库消失（无镜像） |
| `misakaio/chnroutes2` | 仅交叉验证，`role: validation-only`，编译器硬拒绝入路由 | 单文件 HTTP | 解析 + 非空 | **它的抓取失败会中断整个构建**（CI 无缓存），却对路由结果毫无贡献 |
| `core.telegram.org/resources/cidr.txt` | `telegram-ip`（14 条） | 单文件 HTTP | 解析 + 非空 | 无数量异常检测。缩水到 1 条仍会发布 |
| `felixonmars apple.china.conf` | `apple-cn`（与 v2fly `apple@cn` 合并，461 条） | 单文件 HTTP @ master | dnsmasq 严格解析，拒绝通配与非法域名；不导入 DNS 服务器 | 无数量异常检测。**这是唯一一个"上游内容膨胀 = 更多流量被判 DIRECT"的源**，方向上比缩水更危险 |
| `Koolson/Qure` | 仅图标 URL 引用 | 客户端运行时拉取 | — | 图标失效不影响路由 |

### 5.2 三个具体问题

**(1) CI 里的 last-known-good 从不生效。**
`upstream.py:fetch_text_source()` 在网络失败且本地已有缓存时会 `warnings.warn(... using its cached source)` 并继续。但 `.gitignore` 里有 `.cache/`，`.github/workflows/update.yml` 只对 pip 做了 `cache: pip`，**没有对 `.cache/` 做 `actions/cache`**。所以每次定时任务都是冷启动，任何一个上游（含只做验证的 misakaio）一次 5xx 或超时，就会让 `lane build --refresh` 失败 → 当天六端全部规则都不更新。这条路径在本地开发时有效、在生产里无效，属于典型的"保护措施装在了没有用的地方"。

**(2) 单文件源没有异常熔断，与 CN-IP 的保护强度不对称。**
CN-IP 有 1% 地址空间熔断，而 `apple_cn` 从 461 条变成 4,610 条或 46 条都会被静默发布。考虑到 `apple-cn` 的策略是 `DIRECT` 且位置很靠前（第 4 位），一次上游污染的直接后果是"一批本该走代理的域名被判直连"。这与项目已经确立的"不能让上游一次异常直接破坏用户配置"原则不一致。

**(3) v2fly 的失败没有缓存回退。**
`prepare_git_source()` 在 `refresh and not offline` 分支里直接 `_run(fetch)` + `_run(merge --ff-only)`，任一失败即抛错，没有像 `prepare_cidr_history_source()` 那样 `try/except` 后回退到已有 clone。对一个每日构建来说，这让 v2fly 的一次强推就能卡住流水线。

### 5.3 规则质量抽查

我按"被更早规则集以**不同策略**抢先命中"的口径重算了一遍跨规则集遮蔽（`metadata.json` 现有的 `previous_ruleset_*_candidates` 不区分策略是否相同，因此看不出这一层）：

| 被遮蔽的规则集 | 异策略遮蔽条数 | 主要来源 | 判定 |
|---|---:|---|---|
| `streaming` | 13 | `apple-cn`(13) | **缺陷，见 L-01** |
| `emby` | 1 | `lan`(1，`plex.direct`) | 正常（v2fly `private` 收录 `plex.direct`，Plex 用它解析到局域网地址） |
| `china` | 2 | `tiktok`(`analytics.tiktok.com`)、`brokerage`(`qtlcdn.com`) | 正常（业务规则优先是设计意图） |
| `developer` | 26 | `apple-cn`(16)、`ai`(9)、`social`(1) | 主要是 Apple 大陆开发者 CDN，直连是对的 |
| `google` | 265 | `youtube`(179)、`developer`(45)、`ai`(41) | 正常（更具体的业务组优先） |
| `microsoft` | 187 | `developer`(132)、`gaming`(45)、`ai`(10) | 正常 |

## 7. 性能审计

先声明证据边界：**本节不给出任何"省电多少""快几倍"的数字**，本轮没有真机测量条件，任何此类说法都会是推断。

### 7.1 客观量

- 每次规则更新，Stash 发起 **31** 个 HTTP 请求（22 个逻辑规则集按 behavior 拆成 31 个 provider），其余五端各 **22** 个。总载荷 936 KB（Egern）～1.7 MB（QX）。
- 最大单文件：QX `proxy.list` 848 KB、Stash `proxy.list` 752 KB（后者不被引用）、Stash `proxy-domain.list` 444 KB（被引用）。
- 规则总量 51,206 条，其中域名类约 41,700 条、IP 类约 9,470 条、正则 174 条。
- Stash 的 22 个规范文件**不被主配置引用**，因此不进入设备侧的下载与内存路径。

### 7.2 逐项判断

**provider 数量（31 vs 22）**：Stash 多出的 9 个请求换来的是"绝大多数条目走专用域名/IP 索引"。Stash 官方文档对 `domain` / `ipcidr` 的表述是"针对大量数据做了特别压缩与优化，条目多时应优先使用"，并给出 `classical` 为"Average/Average"的定性分级——**官方只给了等级，没有给百分比**，Lane 的 `DECISIONS` D3 也是这么写的，这个措辞是准确的，不应该改成量化承诺。

**text vs yaml vs MRS**：Stash 自 2025 年 5 月起支持 `format: mrs`，但**只支持 `behavior: domain` 与 `ipcidr`**——`classical` 载荷仍必须是文本。也就是说 Lane 即使切 MRS，也只能覆盖 31 个 provider 中的 domain/ipcidr 部分，`-classical` 必须留着，规则集数量不变，只是多出一条"需要 mihomo 工具链在 CI 里生成二进制"的依赖，并且产物从可 `grep` 变成不可审计。同时官方对 `domain-text` / `ipcidr-text` 的评价已经是"特别优化"，MRS 相对它的增量收益没有公开量化材料。**结论：维持 text，不切 MRS。** 若日后要做，应作为**额外**产物（`dist/stash/rules-mrs/`）供高级用户自行引用，而不是替换默认引用。

**domain / ipcidr / classical 的实际影响**：拆分本身是对的。当前 174 条正则全部落在 `-classical`，占总量 0.34%，`classical` 的检索成本被限制在极小的集合里——这个结构比"全 classical"或"全 domain 但丢正则"都好。

**正则数量与位置**：174 条中 158 条在 `proxy`，位置很靠后，只有未被前 20 个规则集命中的请求才会走到。成本可接受。

**DNS 解析触发条件**：`lan` / `brokerage-ip` / `telegram-ip` 带 `no-resolve`，`cn-ip` 有意不带。这意味着一个未被任何域名规则命中的域名请求，会在 `cn-ip` 处触发一次解析。这是 D1 有意为之，且 Surge 官方文档明确"域名类规则只检查请求主机名，从不需要 DNS 查询"，说明前 21 个规则集不产生解析开销。当前设计是"把唯一一次解析推到最后"，这是正确的方向。

**大型规则集的查找成本**：`proxy`(25,902) + `china`(8,199) + `cn-ip`(9,374) 占了 84%。Stash 上它们分别走 domain 索引和 ipcidr 索引；其余五端走各自内核的原生结构。

**是否需要六端差异化优化**：目前只有 Stash 做了 behavior 拆分。Surge 官方文档记载 `DOMAIN-SET`"在内容非常多时通过特殊优化提供巨大的性能提升"，看起来是 Surge/Shadowrocket 的对应能力。**但 QuixoticHeart/rule-set（同样覆盖这六端）的文档明确写：Surge、Loon 的 DOMAIN-SET 与 RULE-SET"性能与内存占用已无明显差别"，因此没必要做细粒度拆分。** 两条证据方向相反，一条来自官方定性描述、一条来自同类项目的实践结论。在没有真机测量之前，任何一边都不构成 Lane 改动的依据 → 归入 P2「需要实验」，不进 P1。

**重复解析 / 重复加载**：未发现。每个逻辑规则集在每端只出现一次；Stash 的规范文件不被引用；`write_if_changed` 保证内容不变则不重写、不刷新时间戳，客户端侧的条件请求不会被无意义地击穿。

### L-01 `apple-cn` 抢占 Apple Music / Apple TV+ 的 Streaming 规则

1. **编号与标题**：L-01 · `apple-cn` 抢占 Apple Music / Apple TV+，与 D2 记录的意图相反
2. **类型**：**已确认缺陷**
3. **当前实现**：`config/rulesets.yaml` 中 `apple-cn` 位于第 4 位（`lan` / `custom-direct` / `custom-proxy` 之后），策略 `DIRECT`；`streaming` 位于第 13 位，包含 v2fly 的 `apple-tvplus` 与 `apple-music`。
4. **证据**：
   - `dist/stash/rules/apple-cn-domain.list` 含 `+.music.apple.com`、`+.itunes.apple.com`；`dist/stash/rules/streaming-domain.list` 含 `music.apple.com`、`play.music.apple.com`、`amp-api.music.apple.com`、`hls.itunes.apple.com`、`uts-api.itunes.apple.com` 等 13 条被完全遮蔽的条目。
   - 六端首次命中重放：`music.apple.com` → `apple-cn / DIRECT`（Stash、Loon、Shadowrocket、Surge、QX、Egern 全部一致）。
   - 来源追踪：`curl https://raw.githubusercontent.com/felixonmars/dnsmasq-china-list/master/apple.china.conf | grep apple.com` 返回 `server=/itunes.apple.com/114.114.114.114` 与 `server=/music.apple.com/114.114.114.114`。**这两条来自 DNS 加速清单，不来自 v2fly `apple@cn`。**
   - `docs/DECISIONS-2026-08-30.md` D2 原文："Apple TV+、Apple Music 等更具体的业务规则仍按既有优先级先匹配。"
5. **对照**：这与 Lane 自己对 GoogleCN 做出的判断是同一类错误——"国内 DNS 能解析"≠"应该直连"。`NOTICE.md` 已经写明 Apple 的情况不同（其条目解析到可直连的大陆 CDN），这对 App Store / iCloud 成立，但对 Apple Music / Apple TV+ 这类**内容按区域授权**的服务不成立：能连通不代表用户想走直连。
6. **影响平台与场景**：六端全部。用户在 `Streaming` 组里选择任何地区节点，对 Apple Music 与 Apple TV+ **完全无效**；跨区订阅内容、Apple TV+ 片库、Apple Music 区域曲库均按大陆路径处理。
7. **风险**：正确性风险（用户显式选择被静默忽略）；无隐私或 DNS 风险；无泄漏。
8. **建议方案**：把 `apple-cn` 从第 4 位移到 `streaming` 之后、`gaming` 之前。我实测了这个改动的完整影响面：461 条 `apple-cn` 条目中，只有 **26 条**会被中间的规则集改判，其中 **9 条归 `streaming`**（正是要修的），**17 条归 `developer`**（`cdn-cn*.apple-mapkit.com`、`researchkit.cn`、`swiftui.cn`、`devstreaming-cdn.apple.com` 等大陆开发者 CDN，改判为 `Developer` 组是**不希望**的）。因此**不要**把 `apple-cn` 一路移到 `apple` 之前，只移到 `streaming` 之后即可：`ai`/`schwab`/`brokerage`/`crypto`/`youtube`/`tiktok`/`emby` 均不与 `apple-cn` 重叠，`gaming` 之后的 `developer` 保持在 `apple-cn` 之后，17 条大陆 CDN 继续直连。**净变化恰好 9 条。**
9. **副作用**：`music.apple.com` 及其子域在中国大陆网络下改走 `Streaming` 组。`Streaming` 默认跟随 `Manual`，因此默认行为从"直连"变为"跟随用户选中的节点"。这正是用户对一个流媒体组的预期，但属于默认路由变化，必须写进升级说明。
10. **是否改变首次命中语义**：**是**（9 条，六端一致）。
11. **是否需要用户重新导入完整配置**：**否**。`config/rulesets.yaml` 的顺序变化会改变主配置里 `RULE-SET` 的排列，因此**主配置需要更新**；但规则集 URL 不变，规则内容仍可独立更新。保守起见应在 README 标注为"建议升级一次主配置"。
12. **所需测试**：新增黄金用例 `music.apple.com → streaming / Streaming`、`hls.itunes.apple.com → streaming / Streaming`、`apps.apple.com → apple-cn / DIRECT`（回归，确认 App Store 仍直连）、`cdn-cn.apple-mapkit.com → apple-cn / DIRECT`（回归，确认大陆 CDN 未被 `developer` 抢走）。四条都应按 L-06 在六端求值。
13. **优先级**：**P0**
14. **置信度**：**高**（产物、上游、文档三方交叉验证）

### L-02 四端省略 `lan` 单标签主机名正则，裸主机名被代理

1. **编号与标题**：L-02 · Loon / Shadowrocket / Surge / QX 上的裸主机名穿透到 `Final`
2. **类型**：**已确认缺陷**（跨端语义不一致）
3. **当前实现**：`render.render_rule()` 对 `kind == "regexp"` 且 `target != "stash"` 返回 `None`（Egern 走独立的 YAML 渲染路径，保留正则）。`lan` 规则集含 v2fly `private` 的 `regexp:^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$`，即"任意单标签主机名"。
4. **证据**：
   - `dist/stash/rules/lan-classical.list` 只有一行：`DOMAIN-REGEX,^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$`。
   - `dist/report.json` 记录 `loon/shadowrocket/surge/qx` 各省略 `lan: 1`。
   - 六端重放：`nas` → Loon/SR/Surge/QX 为 `FINAL / Final`，Stash/Egern 为 `lan / DIRECT`；`router` 同。
   - 缓解事实：`dist/stash/rules/lan-domain.list` 已含 `+.lan`、`+.local`、`+.internal`、`+.home.arpa`、`+.localdomain`，所以 `nas.local` / `nas.lan` 在六端都正确直连。**只有不带点的裸主机名发散。**
5. **对照**：Surge 5 疑似提供 `HOSTNAME-TYPE` 规则（取值含 `SIMPLE`），可写成 `HOSTNAME-TYPE,SIMPLE,DIRECT`；这与已被明确否决的 `[General] exclude-simple-hostnames` 是两个不同机制。Loon / Shadowrocket / QX 官方文档中未见等价规则类型（QX 官方 `sample.conf` 的规则类型清单已逐条核对，无此项）。
6. **影响平台与场景**：Loon、Shadowrocket、Surge、Quantumult X。场景：`http://nas:5000`、`ssh router`、局域网打印机、Windows/NetBIOS 短名访问。后果是连接失败**且**内网主机名被发送给代理节点。
7. **风险**：轻度信息泄漏（内网主机名出网）+ 功能失败。不涉及凭据。严重度受限于"用户是否使用裸主机名"——多数用户通过 IP 或带点域名访问，而这两条路径已经被 `lan` 的 CIDR 与 `+.lan` 覆盖。
8. **建议方案**：
   - 第一步（零风险）：在 README 与 `dist/report.json` 的 `notes` 里明确写出这条差异，并给出用户可自行添加的一行本地规则。
   - 第二步（需实测）：若 Surge 的 `HOSTNAME-TYPE,SIMPLE` 确认可用且可写在 `RULE-SET` 文件中，为 Surge 单独发出。若只能写在主配置的 `[Rule]` 段，则写在 `[Rule]` 段最前（Lane 目前 `[Rule]` 段只有 `GEOIP,CN,DIRECT` 和 `FINAL,Final`，加一行不破坏远程规则的顺序语义）。
   - **不建议**为此引入 `exclude-simple-hostnames`（已被明确否决，且它是全局开关，语义比一条规则更宽）。
9. **副作用**：若在 Surge 加 `HOSTNAME-TYPE,SIMPLE,DIRECT`，所有单标签主机名强制直连——这正是 Stash/Egern 当前的行为，属于向已有语义对齐，不是新语义。
10. **是否改变首次命中语义**：**是**，但方向是让四端**向 Stash/Egern 靠拢**，消除发散。
11. **是否需要用户重新导入完整配置**：若改动落在主配置 `[Rule]` 段，**是**（仅 Surge）。若只做文档，**否**。
12. **所需测试**：六端黄金用例 `nas`、`router`、`nas.local`、`nas.lan`；并在 `report.json` 断言 `lan` 的省略数与文档说明同步。
13. **优先级**：**P1**
14. **置信度**：**高**（发散是实测的）；Surge 修复手段的置信度为**中**（`HOSTNAME-TYPE` 需实测）

### L-03 174 条 DOMAIN-REGEX 的逐条转换白名单

1. **编号与标题**：L-03 · 用逐条白名单而非全局猜测，收敛 13 条会改变策略的正则差异
2. **类型**：**高价值改进**
3. **当前实现**：所有 `regexp` 规则在四端一律丢弃并只做计数（`report.json`）。
4. **证据**：见 §4.3 的完整逐条表。核心数据：174 条中 158 条在 `proxy`（策略 == `Final` == `MATCH`，省略不改变最终出口）；16 条在其他集合，其中 4 条本就是死规则、2 条可无损枚举、9 条可用极窄 `DOMAIN-KEYWORD` 覆盖、1 条（`lan`）无等价写法（归 L-02）。
5. **对照**：上表 10 个参考项目**没有一个**做跨客户端的正则等价转换；blackmatrix7 的 QX 产物使用 `HOST-WILDCARD`，说明"按目标端选择更合适的原生类型"是业界做法，但它做的是格式选择而非语义转换。因此 Lane 若要做，必须自带证明，不能引用先例。
6. **影响平台与场景**：Loon、Shadowrocket、Surge、Quantumult X。场景：Netflix 的 `apiproxy-*` / `ichnaea-web-*` API 端点、Apple/Epic 的 Akamai 边缘、ChatGPT 的 Azure WebPubSub 长连接、AWS 中国区 DNS、AWS ECR。
7. **风险**：转换本身有"扩大匹配范围"的风险（`DOMAIN-KEYWORD` 不锚定后缀）。表中已逐条标注哪几条是无损、哪几条是轻微扩大。不做转换的风险则是持续的跨端不一致。
8. **建议方案**：在 `config/rulesets.yaml` 或一个新的 `config/regex-fallbacks.yaml` 里建立**逐条**映射（key 为正则原文，value 为替代规则列表），并且：
   - 替代规则**只对缺少正则能力的目标端发出**，Stash / Egern 继续使用原正则（保证语义最强的两端不被降级）；
   - 白名单里没有的正则**继续省略**，不做任何推断；
   - 每条映射必须配一条六端黄金用例。
   优先落地"4 条死规则确认 + 2 条无损枚举"，这部分零风险；`DOMAIN-KEYWORD` 那 9 条可作为第二批。
9. **副作用**：`DOMAIN-KEYWORD` 在部分内核上比后缀匹配更贵（子串扫描）。9 条的量级可以忽略，但**不应把这个机制推广到 `proxy` 的 158 条**。
10. **是否改变首次命中语义**：**是**，且是有意为之——让四端向 Stash/Egern 对齐。
11. **是否需要用户重新导入完整配置**：**否**（只改规则文件内容，URL 与顺序不变）。
12. **所需测试**：每条映射一条六端黄金用例；外加一条"白名单里的正则原文必须真实存在于当前编译结果中"的断言，防止上游删掉正则后白名单变成僵尸配置。
13. **优先级**：**P1**（死规则确认 + 无损枚举）/ **P2**（`DOMAIN-KEYWORD` 那 9 条）
14. **置信度**：**高**（转换表由产物直接推导）

### L-04 地区节点正则的假阳性

1. **编号与标题**：L-04 · `台` / `日` / `美` 的裸字匹配与已确立的"新加坡先例"不一致
2. **类型**：**已确认缺陷**
3. **当前实现**：`config/policies.yaml` 的 region pattern 中，Taiwan 含裸 `台`、Japan 含裸 `日`、United States 含裸 `美`；`filters.region_filter()` 包成 `(?i)^.*(?:PATTERN).*$`。Singapore 已经**刻意**避开裸 `新`（注释写明是为了不误吃 `新北`）。
4. **证据**（用 `build_filters()` 实跑真实节点名）：

   | 节点名 | 匹配到的地区组 |
   |---|---|
   | `香港-中转平台01` | **Hong Kong 与 Taiwan（同时）** ← 平**台** |
   | `烟台联通中转` | **Taiwan** ← 烟**台** |
   | `台州电信中转` | **Taiwan** ← **台**州 |
   | `剩余流量 到期日 2026-12-01` | **Japan** ← 到期**日** |
   | `官网 https://example.com 剩余日 30` | **Japan** ← 剩余**日** |
   | `南美巴西 BR-01` | **United States** ← 南**美** |
   | `邮件订阅 info@jp-mail.com` | **Japan** ← `@jp-` 满足词边界 |
   | `新北 TW01` | Taiwan（正确） |
   | `Russia RU-1` | 无（正确，词边界有效） |

5. **对照**：`config/policies.yaml` 自己的注释就是最好的对照——Singapore 因为 `新` 会抢走 `新北` 而改用完整词 + 中转简称枚举。同一条推理没有应用到 `台` / `日` / `美`。
6. **影响平台与场景**：六端全部（所有客户端都用同一份正则）。README 明确写 `Manual` **不排除**流量、到期、高倍率或维护信息项，所以订阅里的信息条目一定会存在，并被地区组的裸字匹配吸收。后果：`XX Auto`（url-test）会把一个不可用的"信息条目"当成候选节点参与测速；`XX Manual` 里出现明显不属于该地区的条目。
7. **风险**：可用性风险（自动组选中不可用节点）+ 使用体验风险。不涉及路由正确性或泄漏。
8. **建议方案**：沿用新加坡的做法，把裸字换成"完整词 + 中转简称枚举"：
   - Taiwan：`台湾|臺灣|台北|臺北|新北|彰化|Taiwan|Taipei|沪台|深台|京台` + 现有 `TW` 词边界，**去掉裸 `台`**；
   - Japan：`日本|东京|大阪|埼玉|名古屋|Japan|Tokyo|Osaka|沪日|京日|深日|广日|杭日` + `JP` 词边界，**去掉裸 `日`**；
   - United States：`美国|美西|美东|United States|洛杉矶|圣何塞|西雅图|芝加哥|纽约|达拉斯|凤凰城|硅谷|沪美|京美` + `US/USA` 词边界，**去掉裸 `美`**（`南美巴西` / `美洲` 不再命中）。注意保持只用正向枚举，不要引入 `(?!...)` 之类的断言——六端的节点名匹配引擎对断言的支持没有统一保证，而现有 `(?i)` 已是既成事实。
   全部保持"只做正向匹配、不引入排除词"的既定原则。
9. **副作用**：某些机场用的罕见简称可能不再命中（例如只写"台"一个字的节点）。这是可接受的权衡——漏配一个节点只是它不出现在地区组里（仍在 `Manual` 中可选），而误配会污染自动测速。
10. **是否改变首次命中语义**：**否**（不涉及规则匹配，只影响策略组成员筛选）。
11. **是否需要用户重新导入完整配置**：**是**（正则写在主配置里）。建议与其他主配置改动合并成一次升级。
12. **所需测试**：把上表 9 个节点名（含正例与反例）直接加进 `tests/test_filters.py`，作为断言而不是注释。
13. **优先级**：**P1**
14. **置信度**：**高**（用项目自己的 `build_filters()` 实跑得出）

### L-05 单文件上游缺熔断，且 CI 无 last-known-good

1. **编号与标题**：L-05 · 上游保护不对称：文本源无异常熔断，CI 从不使用缓存回退
2. **类型**：**高价值改进**
3. **当前实现**：`upstream.fetch_text_source()` 对下载内容只做 `parse_text_source()`（格式 + 非空）；网络失败时若本地有缓存则回退。`.gitignore` 含 `.cache/`；`update.yml` 只做 `cache: pip`。
4. **证据**：
   - `src/proxyrules/upstream.py:126-150`：文本源无任何数量或覆盖率比较。
   - `.github/workflows/update.yml`：无 `actions/cache` 步骤 → 每次运行 `.cache/` 为空 → `fetch_text_source()` 的 `if not target.exists(): raise UpstreamError` 分支必然生效。
   - `src/proxyrules/build.py`：三个文本源（含只做验证的 `cn_ipv4_reference`）任一失败即中断整个 `build_project()`。
   - 对照 `prepare_cidr_history_source()`：七日窗 + 1% 对称差熔断 + staging + 原子替换 + 克隆失败回退，保护强度差距明显。
5. **对照**：参考项目普遍是"抓最新一份就发布"，在这一项上 Lane 已经领先；问题不是"没做"，而是**只在一个源上做了**。项目自身在 PR #2 建立的原则是"不能让上游一次异常直接破坏用户配置"——这条原则应该一致地适用。
6. **影响平台与场景**：六端全部。两种失效：
   - **可用性**：misakaio（只做交叉验证、对路由零贡献）一次超时 → 当天全部规则不更新，且只有一封 workflow 失败邮件。
   - **正确性**：`apple.china.conf` 若被污染或大幅膨胀，新增条目会以 `DIRECT` 策略、在第 4 位发布，静默把本应代理的域名改成直连。
7. **风险**：正确性 + 可用性。`apple_cn` 那一支带有真实的供应链影响面。
8. **建议方案**（三项，可拆开做）：
   - **(a) CI 缓存**：在 `update.yml` 加 `actions/cache`，key 覆盖 `.cache/text` 与 `.cache/history`，让 `upstream.py` 里已经写好的回退逻辑真正生效。这是投入最小、收益最大的一条。
   - **(b) 文本源数量熔断**：给 `sources.yaml` 的文本源加可选的 `max_change_percent`（例如 `apple_cn: 20`、`telegram_cidr: 50`），与上一次已发布的规则数或地址覆盖比较，超阈值时沿用缓存并在 `metadata.json` 记录一条告警，或按 CN-IP 的做法要求显式 `--accept-*` 参数。基线数据已经在 `metadata.json` 里（`apple-cn: 461`、`telegram-ip: 14`）。
   - **(c) 让验证源失败不阻断构建**：`cn_ipv4_reference` 的 `role` 已经是 `validation-only`，抓取失败时应把 `cn-ip-validation.json` 的 `status` 记为 `unavailable` 并继续，而不是让整个构建失败。
   - **(d) v2fly fetch 失败回退**：给 `prepare_git_source()` 的 `refresh` 分支加 `try/except`，失败时沿用已缓存的 clone 并 `warnings.warn`，与文本源行为对齐。
9. **副作用**：(b) 引入一个新的"可能需要人工确认"的闸门。阈值定得太紧会造成和 CN-IP 熔断一样的"每天失败"体验，因此建议 (b) 的默认行为是**沿用缓存 + 记录告警**，而不是中断构建。
10. **是否改变首次命中语义**：**否**。
11. **是否需要用户重新导入完整配置**：**否**。
12. **所需测试**：模拟"上游条数骤降 80%"与"骤增 10 倍"两种情形，断言产物不变且告警被写入；模拟验证源 404，断言构建成功且 `cn-ip-validation.json.status == "unavailable"`；模拟 v2fly fetch 失败，断言回退到缓存 revision。

### L-06 黄金用例只覆盖 Stash；缺少异策略遮蔽报告

### L-07 发布、回滚与分发

1. **编号与标题**：L-07 · 产物与源码同分支、无存活检查、依赖与 Action 未锁定
2. **类型**：**可选增强**
3. **当前实现**：`dist/` 提交在 `main`；`config/project.yaml` 的 `raw_base` 为 `.../Lane/main`；`update.yml` 用 `actions/checkout@v4` / `actions/setup-python@v5`；依赖为宽松版本范围；`validate.py` 只校验 URL 字符串与清单一致，从不发起请求。
4. **证据**：`config/project.yaml:5`；`.github/workflows/*.yml`；`pyproject.toml:13-17`；`src/proxyrules/validate.py` 全文无网络调用。
5. **对照**：Loyalsoldier 用 `release` 分支、MetaCubeX 用 `meta`/`sing`/`release` + Releases、SukkaW 用独立 CDN + 官方镜像、QuixoticHeart（同样覆盖这六端）用 `ruleset` 分支 + jsDelivr。**四个参考项目都做了产物与源码分离，Lane 是唯一没做的。**
6. **影响平台与场景**：六端全部。具体场景：① 一次代码改动 + 重新生成会立刻对所有用户生效，没有灰度；② 路径改名类事故（Lane 已经发生过两次：`rules-full`/`rules-profile` → `rules`，ProxyRules → Lane）没有自动检测；③ `raw.githubusercontent.com` 在部分大陆网络下不可达，而**首次导入配置时用户还没有可用节点**。
7. **风险**：发布事故风险 + 首次使用体验风险。当前 fail-closed 的构建流程已经挡住了绝大多数坏数据，所以这一条不是紧急项。
8. **建议方案**（按性价比排序）：
   - **(a) 发布后 URL 存活冒烟检查（最高性价比）**：在 `update.yml` 的推送步骤之后，对六端全部 `RULE-SET` URL 与六份主配置 URL 各发一次 `HEAD`，非 200 则让 workflow 失败并告警。约 130 次请求，几秒钟。这条能兜住所有"路径改了但没同步"的事故。
   - **(b) 产物哈希清单**：在 `metadata.json` 里增加 `artifacts.files: {path: sha256}`，覆盖每个已发布的规则文件与主配置。目前 `metadata.json` 只记录**输入**摘要，用户与镜像无法校验下载到的**输出**。实现成本极低（`_directory_digest()` 的逻辑已经存在）。
   - **(c) 依赖与 Action 锁定**：`PyYAML==6.0.x` 精确固定（YAML 序列化行为直接决定 Stash/Egern 产物的字节形态），Action 固定到 commit SHA。
   - **(d) release 分支**：把 `dist/` 推到独立分支并把 `raw_base` 指向它。**收益中等、迁移成本高**（所有已保存的用户配置里的 URL 都要变，等于再来一次全量升级）。建议**暂缓**，除非日后有其他理由必须做一次全量迁移，届时顺带完成。
   - **(e) CDN / 镜像**：jsDelivr 有 12 小时缓存延迟，会削弱"每日更新"的意义；且 jsDelivr 在大陆的可用性本身也不稳定。建议**不改默认 URL**，只在 README 增加一段"若 `raw.githubusercontent.com` 不可达，可临时改用 X"的说明，把选择权交给用户。
   - **(f) 回滚**：在 README 增加一节，写明"发现坏产物时 `git revert` 该次 `chore: update generated rules` 提交并推送，客户端下次更新即恢复"。零成本。
9. **副作用**：(a) 会让 workflow 依赖 GitHub raw 的可用性，可能引入偶发失败；建议加重试。(d) 会强制一次全量用户迁移。
10. **是否改变首次命中语义**：**否**（(d) 除外，它只改 URL 不改语义）。
11. **是否需要用户重新导入完整配置**：(a)(b)(c)(f) **否**；(d) **是**。
12. **所需测试**：(b) 增加"哈希清单与实际文件一致"的 `lane check` 断言；(a) 属于 CI 步骤，无需单测。
13. **优先级**：**P1**（(a)(b)(f)）/ **P2**（(c)）/ **暂缓**（(d)(e)）
14. **置信度**：**高**（(d)(e) 的取舍判断为**中**，取决于维护者对迁移成本的容忍度）

### L-08 Surge DOMAIN-SET 与 Stash MRS

1. **编号与标题**：L-08 · 两项"看起来该做"的性能优化，证据尚不支持
2. **类型**：**需要实验**
3. **当前实现**：Surge / Shadowrocket 使用 `RULE-SET`；Stash 使用 `format: text` 的 domain/ipcidr/classical provider。
4. **证据与对照**：
   - Surge 官方 `Domain-based Rule` 文档：`DOMAIN-SET` "只能包含 DOMAIN 与 DOMAIN-SUFFIX 两种形式，使用特别优化的逻辑，在内容非常多时提供巨大的性能提升"——**定性，无量化**。
   - QuixoticHeart/rule-set（覆盖同样六端）文档：Surge、Loon 的 DOMAIN-SET 与 RULE-SET "性能与内存占用已无明显差别"，因此不做细粒度拆分——**同类项目的实践结论，与官方描述方向相反**。
   - Stash 支持 `format: mrs`，但**仅限 `behavior: domain` 与 `ipcidr`**；`classical` 必须保持文本。Stash 官方对 `domain-text` / `ipcidr-text` 的评价已经是"针对大量数据特别压缩优化"。
5. **影响平台与场景**：Surge / Shadowrocket（DOMAIN-SET）、Stash（MRS）。
6. **风险**：DOMAIN-SET 会让每个逻辑规则集在 Surge 上拆成 2–3 个文件（域名 / IP / 其他），请求数从 22 升到约 45，抵消部分收益；MRS 会引入 mihomo 工具链依赖并让产物不可 `grep` 审计。
7. **建议方案**：**本轮不做。** 若日后要做，先在真机上量一组可复现数据（冷启动时间、`rules` 内存占用、规则重载耗时），A/B 对比同一份规则的两种格式，把数据写进 `docs/`，再决定。MRS 若做，应作为**额外**产物目录供高级用户自选，绝不替换默认引用——这样才不破坏"产物可审计、可回退"的核心价值。
8. **副作用**：见 6。
9. **是否改变首次命中语义**：**否**（纯格式变化）。
10. **是否需要用户重新导入完整配置**：**是**（provider 声明变化）。
11. **所需测试**：格式转换的语义等价测试 + 真机基准。
12. **优先级**：**P2**
13. **置信度**：**高**（"证据不足以支持现在动手"这个结论本身置信度高）

## 10. 不应改动的现有设计

除 §9 Keep 表外，以下实现细节在本轮审计中被逐一验证为有意为之、且实现与文档一致，**不要在没有新证据时改动**：

1. `render.write_if_changed()` + `_with_stable_update_time()`：内容不变则不写文件、不刷新时间戳。这同时保证了构建幂等和"规则更新不逼用户升级主配置"。
2. `compiler._deduplicate()` 只按 `(kind, value)` 去重并按 `RULE_KIND_ORDER` 排序。同一规则集内所有条目共享同一策略，所以重排不影响语义。
3. `text_sources.parse_dnsmasq_domains()` 严格拒绝通配与非法域名、不导入上游 DNS 服务器。这是 `apple_cn` 这条供应链上最重要的一道闸。
4. `validate.py` 对 `dist/` 下所有文件扫描非注释行中的 `REJECT`，只放行四条已批准的 UDP 回落设置。这条守门很少见，很有价值。
5. `lan` 刻意排除 `198.18.0.0/15`（六端的 fake-IP 段）。
6. Surge 用隐藏 `Subscription1` 组 + `include-other-group` + `include-all-proxies`，地区组从 `Manual` 展开而不是取隐藏组的选中项。`validate.py` 对这三层逐一断言。
7. Surge 不写 `icon-url`（官方标注为 Mac 功能），以 iOS 兼容优先。
